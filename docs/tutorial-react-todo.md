# Tutorial: A React to-do app on Saltcorn v2

From a freshly bootstrapped server to a working React to-do app — reading and writing its data
through a typed client Saltcorn generates from your tables. **Everything below happens in a
browser.** You never log into the server host, and there is no `npm` command for you to run.

## Prerequisites: how you start the server

An application is served on **its own subdomain**, so the one thing that has to be decided when
the server starts is the domain those subdomains sit under:

```bash
saltcorn serve --base-domain localhost
```

`--base-domain localhost` turns on subdomain routing, so an app with subdomain `todo` is
reachable at `http://todo.localhost:3000` — browsers resolve `*.localhost` to 127.0.0.1. Without
a base domain the server has no way to address an app, so it serves the admin UI only.

That is the whole command line. Sign in to the admin UI at `http://localhost:3000`.

## Step 1 — Add a file store

Your app's source lives in a **file store**. Create one in the admin UI, under **File stores →
New file store**:

| Field | Value |
|---|---|
| Name | `apps` |
| Description | `Application source` |
| Backend | `local` |
| **Directory** | `/srv/apps` |
| **Create the directory if it does not exist** | ✔ |

Save. The store is connected immediately — no restart — and the directory is created for you if
it does not exist. (Ticking that box is deliberate rather than automatic: without it, a typo'd
path is an error instead of a new empty store.)

The list shows it as connected, with a **Browse** button into the file manager. A store can also
be connected at startup with `--file-store apps=/srv/apps`, which is handy for scripted
deployments; a store made either way works the same everywhere else.

## Step 2 — Build the data model

In the admin UI, go to **Tables**:

1. Type `tasks` in **New table name** and press **Create table**. New tables get an auto `id`
   primary key (`bigint generated by default as identity`), so rows are addressable — that is
   what makes update and delete work.
2. **Open** the table and add two fields:
   - `title` — SQL type `text`, not nullable
   - `done` — SQL type `boolean`, nullable

That is the whole schema. A table's read/write roles govern who may call its API, which matters
in step 5.

## Step 3 — Create the application

Go to **Applications → New application** and fill in:

| Field | Value |
|---|---|
| Name | `Todo` |
| Subdomain | `todo` |
| Framework | **React** |
| **File store** | `apps` |
| **Project directory** | `todo` |
| Tables | `tasks` |
| APIs (Provider / Mount) | `rest` / `/api` |

Two settings for the framework — the store, and a name. Leave the Content-Security-Policy box
empty: React apps get a policy fitted to what their bundler emits.

Press **Create application**. The banner on the applications list says:

> **Application created — Todo**
> scaffolded 14 files into todo (git repository initialised). Build it to install its
> dependencies and serve it.

The server has written a complete Vite + React + TypeScript project into `/srv/apps/todo`,
**generated against your `tasks` table**. Step 6 is a tour of it.

## Step 4 — Build

On the app's row, press **Build**. The server:

1. regenerates the typed client and hooks from *this app's* endpoints,
2. runs `npm install` if the project's dependencies are not installed yet (first build only),
3. runs `npm run build` — which type-checks (`tsc --noEmit`) and then bundles with Vite, and
4. serves the result on the app's subdomain, with no restart.

The build banner shows the log, or the tool's own diagnostics if it fails — npm's registry
error, or the TypeScript error with the file and line.

## Step 5 — Open the app

```
http://todo.localhost:3000
```

You get a sign-in screen, because **routes require a signed-in user unless they say otherwise**.
Sign in with your admin email and password — an app authenticates against the same users as the
admin UI, subject to each table's roles. You then have a Tasks page listing rows, a form to add
one, and a delete button per row.

Add a task. It is in your `tasks` table; open the table in the admin UI and you will see it
there.

## Step 6 — What was generated

Two kinds of file, and the difference matters:

```
todo/
  package.json  vite.config.ts  tsconfig.json  index.html  .gitignore
  src/
    main.tsx        entry point: providers + router
    App.tsx         the shell — header, nav, routes
    routes.tsx      the route list, as data
    auth.tsx        <AuthProvider>, useUser()
    Login.tsx       the sign-in screen
    app.css         plain CSS, custom properties, light + dark
    pages/
      Tasks.tsx     generated from your table's columns
    saltcorn/       ← generated, rewritten on every build
      client.ts     the typed API client
      hooks.ts      typed hooks over it
```

**`src/saltcorn/` is ours.** It is regenerated every build and carries a `DO NOT EDIT` header.
That is what keeps it in step with your schema: add a column to `tasks`, rebuild, and
`TasksRow` has it.

```ts
export type TasksRow = {
  id: number;
  title: string;
  done?: boolean | null;
};

export function useTasks(): Query<TasksRow[]>;
export function useCreateTasks(): Mutation<Partial<TasksRow>>;
export function useUpdateTasks(): Mutation<{ id: number; body: Partial<TasksRow> }>;
export function useDeleteTasks(): Mutation<number>;
```

The hooks cache per table and invalidate on write, so a create refreshes the list with no
`refresh()` of your own:

```tsx
const { data, loading, error } = useTasks();
const create = useCreateTasks();
// create.run({ title, done: false }) — the list re-fetches itself
```

**Everything else is yours** from the moment it exists. The scaffold writes those files once and
never touches them again, so edit them freely. Adding a column updates the *types*; putting it on
the page is your call.

Routes are a list, not a directory convention:

```tsx
export const routes: AppRoute[] = [
  { path: "/", label: "Tasks", element: <TasksPage /> },
  { path: "/login", label: "", element: <Login />, public: true },
];
```

`public: true` is the opt-out from sign-in. Leaving it off means "signed in required", so a route
you forget about is closed rather than open. Client-side auth is a convenience only — every
request is authorized again by the server, against the table's roles.

## Step 7 — Edit it

The loop is **edit file → build → view**:

1. On the app's row, click the source link (`apps/todo`) to open the file manager there.
2. Edit `src/pages/Tasks.tsx` — add a column, change the layout.
3. Press **Build** on the app's row.
4. Reload `todo.localhost:3000`.

No restart, and other applications keep serving throughout. If you would rather work over SSH or
with your own editor, the project is an ordinary git repository on disk; nothing here depends on
having gone through the file manager.

## Things that trip people up

- **Reachability** is entirely `--base-domain`. Without it you only ever see the admin UI.
- **API access** follows each table's read/write roles. A list that 401s means the caller's role
  is below the table's read role — sign in, or lower the requirement on the table.
- **Scaffolding never overwrites.** Pointing a second application at a project directory that
  already has files in it creates the application but refuses to generate into it, and says so.
  Pick another project name, or point the app at the project that is already there.
- **The first build is the slow one** — it installs dependencies. Later builds skip that unless
  `node_modules` has gone away.
- **Building from a terminal**: `saltcorn build-app todo` builds one application by subdomain
  and prints the installer's and bundler's output as it goes. It is the same build the button
  runs, so it is what to reach for in a deploy script — or when a failing build has left the
  app unreachable in a browser. It does not mount anything, so it is safe to run against a
  live deployment's database.

## When React's conventions do not fit

The `react` framework decides your bundler, your router, your data layer and your project
layout. When you need something else — Next.js, SvelteKit, an existing project, a bundler of
your own — use the **`code`** framework, which serves any static bundle you can build:
[tutorial-code-framework.md](tutorial-code-framework.md). You create the project and state where
its source, output and build command are; Saltcorn generates the typed client and serves what
your bundler emits.
